## Additional observations and entity evidence (0.4)

`--snapshot QBL-2025-06-20.xlsx` and `--snapshot QBL-2025-11-22.xlsx` select the two
archived workbooks. The default remains `QBL.xlsx`; every workbook is embedded in the
binary and has its own manifest entry. `srl change` compares all three. Supplier row IDs
are local to each workbook; longitudinal matching uses cleaned name, address and ZIP5.
Capture dates are observation dates. The strict token catalog is shared, so changes in
spelling can appear as product changes. All pipeline counts below describe the default.

`catalog/identities.csv` records each of the 31 candidate pairs: `same` means a supported
duplicate-row sensitivity, `site` means distinct billing rows supporting an entity outage
scenario, and `unresolved` means the evidence does not settle it. `site` does not certify
a physical plant. No verdict changes the strict matrix. `srl entities` separately reports
the effect of merging only `same` pairs and of merging every candidate. The catalogs
are tied to `QBL.xlsx`; `entities` rejects an older selected snapshot.

`catalog/owners.csv` has one source per member and supplies explicit joint-outage
scenarios. Recipient-parent records are reported relationships; they do not establish
outage correlation or failure probability. Identity and owner edges form transitive
entity groups. These scenarios hold all other approvals fixed.

`catalog/usaspending.json` records the name-core and ZIP candidate join, recipient amounts
and reported parents. The complete retrieved awards and supporting extracted records are
retained compressed in `data/evidence`, with hashes in its manifest. Run
`python analysis/check_evidence.py` to check every published amount and link. Full award
amounts are scoped to distinct recipients, with no allocation to suppliers or plants;
they are neither unit prices nor capacity. Fiscal-year windows select activity, not
transaction sums restricted to those years.

See [0.4 findings and review log](findings/2026-10-25-open-work.md) for the numbers,
identification limits and remaining evidence requirements.

## Pipeline

1. **Read** (`src/xlsx.rs`, `src/qbl.rs: read`). A zip-directory reader with raw deflate
   and an XML parser reads the first sheet. Each
   row keeps its sheet row number, which is the provenance of every derived fact.
2. **Harmless normalisation** (`src/qbl.rs`): no meaning changes. Whitespace is Python's
   `str.isspace` set; case folding is lowercase, which equals Python's `casefold` on every
   character of this snapshot (four characters are not ASCII: ¼, an en dash, curly
   quotes). A new snapshot with other scripts needs that check again.
   - whitespace collapsed and case folded;
   - spacing round " - " unified (`WF -Wheat Flour` = `WF - Wheat Flour`);
   - ZIP codes zero-padded to 5 digits (`8518` → `08518`; Excel stored them as numbers).
3. **Identity** (`qbl::records`). A supplier is the key (name, billing address, ZIP5).
   - Rows with equal keys are merged and reported as `same_identity`.
   - Rows whose names agree after removing punctuation and legal suffixes, but whose keys
     differ, are kept apart and reported as `identity_candidate`.
   - A billing address is not a plant. Shared ownership is not inferred.
4. **Semantic interpretation** (`src/catalog.rs`, `data/catalog/mappings.csv`). Every token
   gets a granularity class, a strict product list and a merged product list. Rules apply
   unless the hand-authored mapping file overrides them, and every override carries its
   justification.

## Granularity classes

| Class | Rule | Meaning |
| --- | --- | --- |
| `material` | `^dddddd - ` | numbered USDA material |
| `naics` | `^dddddd x` | NAICS-prefixed commodity code (international programmes) |
| `program` | `^code - name`, code ≤ 5 letters (+digit) | AMS programme code |
| `description` | has a pack or form word (can, pkg, ctn, frz, bulk, lb, …) | material description |
| `commodity` | anything else | named commodity, no specification |
| `broad` | explicit list in `mappings.csv` | names a group of commodities or no product |

Baskets are drawn within one class. A qualification for a broad or commodity token is never
read as a qualification for a narrower product.

## Mapping variants

- **strict** (primary). Product = token, with three exceptions:
  - three lines that each hold two codes (two programme pairs and one material pair) are
    split;
  - a misspelling under the same code is corrected (`temperture`);
  - spacing variants of `TOR1` are unified.
- **merged** (sensitivity). Programme tokens are read as their code, so `WF - Wheat Flour`
  and `WF - Wheat Flour Products` become one product. Ten further judgement calls are
  listed in `mappings.csv` (e.g. `rice products` → RP). The code `PP` is used for both
  *peanut products* and *pasta products*; the merged variant resolves it by name, and this
  is marked as a judgement call.

  `Tyson` rows). The bench reruns every instance with each candidate merged into its match
  (K7).

  10 merged mappings are judgement calls.
- **Mojibake.** One token carries replacement characters from the source
